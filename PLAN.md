# WebMotiv — план

> Название рабочее: до первого развёртывания меняется поиском и заменой.
> Документ живой — решения и ответы офиса дописываются сюда.

## 1. Что делаем

Внутренний веб-сервис для того же офиса, что и WebPricer: заказы радиодеталей, которые проходят
этапы. Сотрудник договорился с покупателем → создаёт заказ по шаблону → заказ идёт по этапам
по порядку; на каждом этапе свой исполнитель заполняет поля, загружает документы или просто
отмечает «Готово». Этапы и их последовательности (шаблоны) настраивают сами сотрудники с нужными
правами.

Заменяет Мотив (motiw.ru) — СЭД общего назначения: офису из неё нужна малая часть, остальное
мешает, и она устарела.

- Одновременно — до ~10 пользователей.
- Требования приходят по частям: основа должна легко расширяться.
- У офиса повышенные требования к безопасности, но не в ущерб удобству (§7).
- Первая версия — демонстрация с ноутбука разработчика. Офис получает только финальную версию и
  ставит её с нуля, без обновления промежуточных.

## 3. Предметная модель

### 3.1. Термины

- **Этап** — шаг заказа: название, описание, исполнитель, набор полей. Этапы лежат в библиотеке;
  один этап может входить в несколько шаблонов.
- **Шаблон** — упорядоченная последовательность этапов из библиотеки («Заказ под поставку»,
  «Заказ со склада»).
- **Заказ** — экземпляр шаблона: шапка (номер, покупатель, ответственный, комментарий) и этапы со
  значениями полей.
- **Ответственный** — сотрудник, который ведёт заказ; по умолчанию его создатель.
- **Роль** — должность (Менеджер, Бухгалтер, Склад…): набор прав (§5) и основание назначать
  исполнителем этапа.

### 3.2. Жизненный цикл заказа

- **Создание:** выбрать шаблон, заполнить шапку. Заказ копирует себе этапы шаблона вместе со
  схемами полей (снимок). Номер — автоматический, вида `2026-0001`. Активным становится первый
  этап.
- **Активный этап** заполняет только его исполнитель: сохраняет черновик сколько угодно, затем
  нажимает «Готово». «Готово» доступно, когда заполнены обязательные поля и нет несохранённых
  правок; перед ним — подтверждение, потому что вернуться нельзя.
- **Завершённый этап** закрыт навсегда (только чтение); активным становится следующий. После
  последнего этапа заказ «Завершён».
- **Видимость:** все этапы — прошлые, текущий и будущие — видны (только чтение) каждому, кто видит
  заказ.
- **Отмена** — отдельное право; отменённый заказ только для чтения. Удаления заказов нет.

### 3.3. Исполнители

Исполнитель задаётся у этапа в библиотеке:

- **роль** — этап может заполнить любой сотрудник с этой ролью;
- **ответственный по заказу** — только ответственный этого заказа (типично для первого и
  последнего этапов).

Подряд идущие этапы с одним исполнителем и дают «диапазон этапов». Главный экран сотрудника —
**«Мои задачи»**: заказы, в которых активный этап ждёт именно его.

### 3.4. Поля этапа

- Типы v1: строка, многострочный текст, число, дата, выбор из списка, флажок, сотрудник, файлы.
- Признаки: обязательное, подсказка.
- Этап без полей — просто отметка «Готово».
- У поля стабильный id: переименование не теряет значения.

### 3.5. Правки этапов и шаблонов

- Правка этапа или шаблона влияет только на новые заказы (снимок).
- В редакторе этапа видно, в каких шаблонах он используется.
- Использованный хоть раз этап или шаблон не удаляется, а уходит в архив; неиспользованный
  удаляется.

### 3.6. Одновременная работа

У заказа есть `version`. Если двое сохраняют один заказ, второй получает «Заказ изменён другим
сотрудником» и видит свежие данные — тихой перезаписи нет.

## 5. Права

Права — фиксированный список в коде; роли — наборы прав, настраиваются в интерфейсе. У сотрудника
может быть несколько ролей. Права читаются из БД на каждый запрос, поэтому изменения действуют
сразу.

| Код                | Что даёт                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------- |
| `orders.create`    | создавать заказы                                                                            |
| `orders.view_all`  | видеть все заказы (без него — только те, где сотрудник ответственный или исполнитель этапа) |
| `orders.manage`    | отменять заказы, менять ответственного                                                      |
| `templates.manage` | библиотека этапов и шаблоны                                                                 |
| `users.manage`     | сотрудники: создание, блокировка, сброс пароля, завершение сеансов                          |
| `roles.manage`     | роли и их права                                                                             |
| `audit.view`       | журнал событий                                                                              |

- Заполнение этапа — не право, а назначение (§3.3).
- Роли по умолчанию: Администратор (все права), Руководитель, Менеджер, Бухгалтер, Закупщик, Склад.
  Для демо `orders.view_all` есть у всех.
- Защита от блокировки системы: нельзя отнять `users.manage` и `roles.manage` у последнего, кто их
  имеет, и заблокировать его.
- Нельзя выдать права, которых нет у тебя самого: назначить или снять роль можно, только если у
  тебя есть все её права; добавить или убрать право у роли — только своё. Иначе сотрудник с
  `users.manage` назначил бы себе роль администратора. В интерфейсе такие флажки неактивны.

## 6. Интерфейс

Основа — дизайн WebPricer: токены, Inter, синий акцент, светлая и тёмная темы, блоки на сером
фоне, разделы в стиле Apple (заголовок над блоком, без разделителей внутри), «Отменить ·
Сохранить» под блоком только при несохранённых правках, без автосохранения.

Отличия от WebPricer:

- **Сайдбар** слева прямо на сером фоне (как в Linear): Мои задачи, Заказы; «Настройка» —
  Шаблоны, Этапы, Сотрудники, Роли, Журнал. Внизу — профиль, тема, выход. Пункты видны по правам.
- **Страница заказа шире колонки 680 px:** слева блок этапов со статусами, в центре выбранный этап,
  справа (или ниже) шапка заказа и история.
- **«Готово»** — новое главное действие: справа в заголовке этапа; активно при заполненных
  обязательных полях и без несохранённых правок; с подтверждением.
- **Цвета статусов** (ожидает / в работе / готово / отменён) — в приглушённом стиле меток
  поставщиков WebPricer.
- **Только десктоп:** с телефона не работают; адаптив не обязателен, но вёрстка не должна ломаться.

Экраны: вход (+ смена временного пароля при первом входе), мои задачи, список заказов (фильтры:
статус, шаблон, текущий этап, ответственный; поиск по номеру и покупателю), новый заказ, заказ,
библиотека этапов и редактор этапа (конструктор полей с перетаскиванием), шаблоны и редактор
шаблона (перетаскивание этапов), сотрудники, роли, журнал, профиль (пароль, мои сеансы).

## 7. Безопасность

Принцип: строго на сервере, незаметно для пользователя. Никаких правил «заглавная + цифра +
символ», принудительной смены пароля раз в N дней и лишних подтверждений — они ухудшают и удобство,
и безопасность (NIST SP 800-63B).

### 7.1. Вход и сессии

- Личные учётки, саморегистрации нет. Сотрудника заводит администратор с временным паролем; при
  первом входе сотрудник задаёт свой. Первый администратор — из `.env` или CLI; сброс пароля — в
  интерфейсе или CLI.
- Пароль: от 12 символов, состав любой, фразы с пробелами можно; проверка по встроенному списку
  распространённых паролей (никуда не отправляется). Кнопка «показать пароль».
- Хэш — scrypt с параметрами OWASP. Параметры хранятся в самом хэше; если они устарели, хэш
  пересчитывается при входе.
- Перебор: лимит по IP и по логину с нарастающей задержкой, а не вечной блокировкой — иначе
  злоумышленник может заблокировать чужую учётку. Для неизвестного логина и неверного пароля —
  одинаковые ответ и время ответа.
- Сессия: случайный 256-битный токен в cookie `HttpOnly; Secure; SameSite=Strict` (с префиксом
  `__Host-` по HTTPS), в БД — только его SHA-256. Новый токен при каждом входе. Тайм-аут
  бездействия (по умолчанию 2 ч, настраивается) и абсолютный срок 12 ч — вход раз в рабочий день.
- Смена и сброс пароля, блокировка сотрудника завершают его сеансы. Сотрудник видит свои сеансы и
  может завершить любой; администратор — сеансы любого сотрудника.
- 2FA (TOTP с «запомнить устройство на 30 дней») — заложена; включаем для администраторов, если
  сервис будет доступен из интернета (вопросы 10, 13).

### 7.2. Доступ

- Всё запрещено по умолчанию: каждый маршрут API явно объявляет нужное право; маршрут без
  объявления не регистрируется (проверка при старте и тест).
- Проверки на уровне объекта: писать можно только в активный этап и только его исполнителю; файл
  скачивает только тот, кто видит заказ; видимость заказов — по `orders.view_all`.
- Тесты матрицы доступа: роль × действие → разрешено или запрещено.

### 7.3. Ввод и вывод

- Все входные данные — через zod в строгом режиме (лишние поля — ошибка); значения этапа
  проверяются на сервере по схеме из снимка; лимиты на длины и количество.
- SQL — только параметризованный (Drizzle; сырой `sql` — только с плейсхолдерами).
- XSS: React экранирует сам; `dangerouslySetInnerHTML` запрещён правилом линтера.
- Заголовки (`@fastify/helmet`): строгий CSP (`default-src 'self'`; скрипты только свои плюс хэш
  встроенного скрипта темы; `object-src 'none'`, `frame-ancestors 'none'`, `base-uri 'none'`),
  HSTS за HTTPS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
  `Permissions-Policy`.
- CSRF: `SameSite=Strict`, обязательный заголовок у изменяющих запросов (как в WebPricer) и
  проверка `Origin`.
- Ошибки — без внутренних подробностей. В логах нет паролей, токенов и значений полей (pino
  redact).
- Все ресурсы свои, без CDN (шрифты — fontsource, как в WebPricer).

### 7.4. Файлы

- Белый список форматов (пока pdf, doc, docx, xls, xlsx, jpg, png). Тип проверяется по сигнатуре
  содержимого, а не по расширению или MIME от браузера. Лимиты размера (по умолчанию 25 МБ) и
  количества.
- Загрузка потоком на диск во временный файл, затем атомарное переименование. Имя на диске —
  UUID, исходное имя только в БД; SHA-256 — для контроля целостности.
- Отдача только через API с проверкой доступа. Встроенный просмотр — только PDF и изображения
  (`Content-Disposition: inline`, `nosniff`, `CSP: sandbox`); остальное — `attachment`. HTML и SVG
  никогда не отдаются inline.
- DOCX просматривается в браузере (docx-preview, отдельный чанк). Старый DOC браузер показать не
  может — только скачивание; конвертация в PDF через LibreOffice — вопрос 6.
- Антивирусная проверка (ClamAV) — по решению офиса (вопрос 14).

### 7.5. Журнал

Единая таблица `events`, только добавление; API на изменение или удаление нет. Пишутся: входы
(успешные и неуспешные, с IP), выходы, изменения сотрудников, ролей и прав, этапов и шаблонов, все
действия с заказами, загрузки и скачивания файлов. Экран «Журнал» с фильтрами — по праву
`audit.view`.

### 7.6. Развёртывание

- Контейнер: приложение работает не от root (как в WebPricer), корневая ФС только для чтения,
  запись — только в `data/` и tmp, `no-new-privileges`, минимум capabilities.
- `TRUST_PROXY` — адреса прокси, а не `true`: иначе при прямом доступе к порту можно подделать
  `X-Forwarded-For` и обойти лимит входа.
- HTTPS — на прокси офиса; cookie `Secure`, HSTS.
- Секреты — только в `.env`. `APP_SECRET` шифрует секреты в БД (TOTP, ключи интеграций).
- Бэкапы: ночной согласованный снимок БД (online backup SQLite) и файлов в `data/backups/`,
  хранится N последних, инструкция восстановления проверена. Копирование на другую машину и
  шифрование — вопрос 15.
- Зависимости: минимум, lockfile, `npm audit --omit=dev` входит в `npm run check`.

### 7.7. Процесс

В конце каждой фазы — проверка по этому разделу и `/security-review`. Новый маршрут API без теста
доступа не принимается.

### 7.8. Формальные требования

Ответ офиса (2026-10-03): формальных требований (152-ФЗ, коммерческая тайна, ДСП, аттестация) нет,
персональных данных, скорее всего, не будет. «Безопасность» — это защита от взлома и
несанкционированного входа, то есть §7.1–7.7. Регуляторных мер не делаем.

## 8. Стек и структура

- `apps/server` — Fastify; `apps/web` — React; `packages/shared` — zod-схемы API и типы, в том
  числе схема полей этапа (общая для сервера и конструктора).
- Как в WebPricer: Node ≥ 22.18 локально, `node:24-slim` в Docker, сервер запускается из
  TS-исходников (type stripping), better-sqlite3, pino, ESLint + Prettier + Vitest,
  `npm run check`.
- Новое: drizzle-orm и drizzle-kit, @fastify/multipart, @fastify/helmet, file-type,
  react-hook-form, @dnd-kit/react, docx-preview.
